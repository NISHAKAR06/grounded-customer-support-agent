# Grounded Customer Support Agent — Development Guide

## 1. Project Philosophy & Core Objective

The **Grounded Customer Support Agent** is a production-grade AI support operations system built specifically for the Hiver SDE Intern Take-Home assignment.

The central mission of this system is to handle customer support inquiries with provable grounding in historical resolved brand conversations, strict validation against hallucinations or policy violations, and an explainable decision engine that routes between automated handling (`AUTO_HANDLE`) and human intervention (`HUMAN_ESCALATION`).

### Primary Principles
1. **The Proof is Worth More Than the System**: Evaluation integrity takes absolute precedence over cosmetics. No fabricated metrics, no fake conversations, no data leakage, and no cherry-picked samples.
2. **Grounding in Historical Reality**: Responses generated by the agent must strictly derive from real, resolved interactions by the selected brand.
3. **Safe Escalation**: Knowing *when not to automate* is as critical as automating. Ambiguity, weak retrieval evidence, customer frustration, or low classification confidence must deterministically trigger escalation to human agents.
4. **Reproducibility**: Any recruiter or evaluator must be able to spin up the system and verify headline benchmarks within 15 minutes without requiring 3M raw tweets.

## 2. Phased Development Lifecycle

To maintain clean engineering hygiene and strict evaluation integrity, development is strictly segmented into sequential phases:

| Phase | Identifier | Focus | Key Output Artifacts |
| :--- | :--- | :--- | :--- |
| **Phase 0** | Project Foundation | Project scaffolding, documentation, design system, core schemas, CI/CD | Base templates, config, logging, specifications |
| **Phase 1** | Dataset Exploration | Kaggle Customer Support on Twitter ingestion, schema validation, brand volume | `notebooks/01_data_exploration.ipynb`, EDA summary |
| **Phase 2** | Brand Selection | Evidence-backed selection of ONE brand based on volume & quality | `docs/brand_selection.md`, updated `DATASET.md` |
| **Phase 3** | Conversation Reconstruction | Thread graph traversal, multi-turn stitching, resolution detection | `notebooks/02_conversation_reconstruction.ipynb`, clean threads |
| **Phase 4** | Intent Taxonomy | Domain-specific intent taxonomy derived from selected brand data | `notebooks/03_intent_taxonomy.ipynb`, taxonomy schema |
| **Phase 5** | Golden Evaluation Set | 150–250 hand-labelled real examples with annotation guidelines | `data/golden/golden_set.jsonl`, `data/golden/README.md` |
| **Phase 6** | Intent Model Training | Majority baseline, TF-IDF + LogReg, and final intent classifier | Trained weights, confusion matrix, per-class F1 |
| **Phase 7** | Historical Retrieval | Dense MiniLM embeddings + FAISS vector index of resolved cases | `models/embedding_model/faiss.index`, Recall@1/3/5 |
| **Phase 8** | Grounded Generation | Gemini Provider + Local LLM Fallback with grounding constraints | Evidence prompt builder, provider abstraction |
| **Phase 9** | Validation & Escalation | Hallucination checks, claim verification, rule-based escalation | `ResponseValidator`, `EscalationPolicy` |
| **Phase 10**| Agent Orchestration | Central pipeline coordinating context, intent, retrieval, reply, decision | `AgentOrchestrator`, end-to-end integration |
| **Phase 11**| Evaluation Harness | Automated multi-model benchmark, LLM-as-Judge, Human Agreement | Evaluation metrics table, Cohen's Kappa / agreement |
| **Phase 12**| Failure & Headline Analysis| Real failure modes and "What is misleading about headline number?" | `report/evaluation_report.md`, `report/failure_analysis.md` |
| **Phase 13**| FastAPI Backend | Production REST API, health probes, and event streaming | Endpoints in `app/api/routes/` |
| **Phase 14**| Jinja2 & B2B SaaS UI | High-contrast black/white interface inspired by Hiver design language | Reusable templates, clean modular CSS |
| **Phase 15**| Live Simulation | Real-time interactive trace: Message → Intent → Evidence → Reply → Route | Real pipeline trace on `/simulate` |
| **Phase 16**| UI Polish & Ergonomics | Typography, state transitions, responsive views, error toasts | Production frontend feel |
| **Phase 17**| Comprehensive Testing | Unit, integration, API, and benchmark validation | Pytest suite across all sub-packages |
| **Phase 18**| Final Reproducibility | Turnkey evaluation script, sample dataset package, polished README | Single-command evaluation verification |

## 3. Local Environment Setup

### Prerequisites
- Python 3.11+ (Python 3.12 or 3.13 supported)
- Git
- Virtual environment (recommended: `venv` or `conda`)

### Installation
```bash
# 1. Clone repository
git clone https://github.com/NISHAKAR06/customer-support-agent.git
cd customer-support-agent

# 2. Create and activate virtual environment
python -m venv venv
# On Windows:
.\venv\Scripts\activate
# On Unix/macOS:
source venv/bin/activate

# 3. Install dependencies
pip install -r requirements.txt
pip install -r requirements-dev.txt

# 4. Configure environment
cp .env.example .env
```
